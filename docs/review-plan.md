# План проведения технического ревьюирования (Code & Document Review)

## 1. Цели ревьюирования
* Выявление логических ошибок, уязвимостей и «запахов кода» (Code Smells) до слияния в ветку `develop`.
* Обеспечение единого стиля оформления кода и документации согласно правилам `.editorconfig`.
* Обмен знаниями и поддержание качества кодовой базы внутри команды.

## 2. Измеримые критерии приемки (Definition of Done)
1. **Стиль и форматирование:** 100% соответствие правилам `.editorconfig` (кодировка UTF-8, отступы 4 пробела, отсутствие лишних пробелов в конце строк).
2. **Размер изменений:** объем одного Pull Request не превышает 300–400 строк кода.
3. **Автоматические проверки:** все шаги CI/CD (Quality Gate) завершены со статусом `Success` (0 критических ошибок).
4. **Документация:** при добавлении нового функционала обновлен файл `README.md` или документация в папке `docs/`.

## 3. Роли и ответственность
* **Автор (Author):** подготавливает изменения, проводит самопроверку (Self-Review), открывает Pull Request и исправляет замечания ревьюера.
* **Ревьюер (Reviewer):** проверяет Pull Request на соответствие критериям приемки в течение 24 часов с момента создания, оставляет конструктивные комментарии или ставит одобрение (Approve).
* **Тимлид (Maintainer):** принимает финальное решение о слиянии (Merge) в ветку `develop` после получения одобрения от ревьюера.

## 4. Процедура эскалации
1. **Уровень 1 (Технические разногласия):** если автор и ревьюер не могут прийти к единому решению в течение 1 рабочего дня, к обсуждению в комментариях PR привлекается Тимлид.
2. **Уровень 2 (Нарушение SLA / Блокер):** если Pull Request ожидает проверки более 48 часов или блокирует критическую задачу, автор присваивает ему метку `urgent` и уведомляет Тимлида для срочного назначения другого ревьюера.
